# Building the prototype ISO

The active development builder produces the same Ubuntu 26.04 LTS/Plasma 6 live system for `amd64` and `arm64`, using architecture-specific kernels, package archives, bootloader packages, build caches, output names, and metadata. Common desktop, AI, visual assets, themes, apps, and configuration are shared. The former XFCE implementation is preserved in branch `legacy/xfce4` and `scripts/build-iso-xfce4-legacy-container.sh`.

Requirements: Docker Desktop with at least 8 GB RAM, 30 GB free disk, and network access. Build a matched release with `./scripts/build-iso.sh --both`; build one architecture with `./scripts/build-iso.sh --arch amd64` or `--arch arm64`. Release builds require a clean committed worktree. `--both` captures one source commit and product version, builds ARM64 then AMD64 with distinct build IDs/manifests, and publishes only verified artifacts. A single-architecture build never advances `latest/` to an incomplete newer release. The helper container uses Ubuntu 24.04 tooling to debootstrap the Ubuntu 26.04 (`resolute`) target; the 24.04 host container completed the bootstrap that failed under the 26.04 host container. AMD64 uses the official Ubuntu archive; ARM64 uses Ubuntu Ports. On Apple Silicon, ARM64 build tools run natively in Docker and AMD64 uses emulation. The scripts preserve separate caches/rootfs trees. Both EFI targets install `mtools`, which `grub-mkrescue` needs for the EFI FAT image. Removing a cache volume discards its cached target rootfs. Set `IFBA_BUILD_CACHE_VOLUME` to use an explicitly named cache volume.

Set the shared product release version in `tools/build_metadata.py` and commit all build inputs before building. Both architectures of a release must embed the same source commit and version; build IDs and hashes remain architecture-specific. `scripts/build-iso.sh --both` is the preferred matched-release command. It captures one HEAD and version, stages each architecture in a distinct filename/metadata file, verifies both, and publishes to `output/versions/vX.Y.Z/{amd64,arm64}/` with `manifest.json`. It refuses dirty source and checks that HEAD did not change during the build. `tools/release_artifacts.py list|verify|migrate` lists, verifies, and safely organizes local artifacts. `output/latest/{amd64,arm64}/` uses symlinks to avoid duplicating ISO files; `release-status.json` states whether both pointers form a matched release. The migrated history currently points to ARM64 v0.3.0 and AMD64 v0.3.1, marked `complete_pair: false` because their source commits differ. Product version 0.3.2 is configured for the next shared build but has no ISO artifacts and must not appear in `latest/` until both matching builds exist. The manifest records source commit, UTC build time, architecture, unique build ID, runtime status, SHA-256, and exact byte size. The builder checks wallpaper, IFBA color scheme, SDDM, Plasma packages, Firefox, IFBA AI, SUAP/AVA launchers, DHCP profile, and build metadata before SquashFS creation.

The Plasma builder includes SDDM, Plasma 6 Wayland and X11 sessions, KWin, Dolphin, Konsole, Discover, System Settings, NetworkManager/audio widgets, a project color scheme and a native Plasma global-theme package. Its first-run layout defines a dark floating bottom panel configured for full-width length, with Kickoff, task switching, the system tray and clock; IFBA AI, Firefox, Dolphin and Konsole are included in task-manager launchers. SDDM starts the live account into the X11 Plasma session for the UTM prototype. The one-time session setup applies the user-supplied wallpaper and layout without resetting later wallpaper preferences. The existing Python/GTK assistant backend/service, Mozilla Firefox DEB and ordinary SUAP/AVA links are preserved. For ARM64 v0.3.0, the ISO structure and AArch64 UEFI payload were checked, but no UTM guest boot has been validated yet; wallpaper, panel styling, SDDM, network, Firefox and assistant startup still need runtime checks.

The Electron source under `app/` is a separate design prototype; the ISO does not include or autostart it. KWin is the compositor and window manager in the new build; no second compositor is installed. Animation modes, window decoration refinements, launcher interactions and background blur have not yet been implemented or validated.

The educational package catalogue is not installed by this image. The GTK assistant settings/chat window, user-scoped D-Bus service, private SQLite data directory, Secret Service integration, NVIDIA text stream, and source-level consent-based visual guidance are included. The visual/X11 dependencies are `python3-xlib`, `python3-pyatspi`, and `at-spi2-core`. The current output ISO must be rebuilt after these changes. The assistant has not made a live authenticated request. The live ISO auto-logs into a shared passwordless `ubuntu` account, so do not configure personal API keys or real student data in this demo; it does not provide per-student account isolation. The current output ISOs do not include the Calamares candidate. The updated build recipe includes an experimental Calamares installer that has not passed a real installation, reboot, and login test; see [`INSTALLER.md`](INSTALLER.md). The generated IFBA identity is provisional. Do not boot this image on real hardware or present it as an official IFBA release.

The build removes the container's systemd-resolved stub before SquashFS creation so the live guest can configure DNS itself. It does not embed host Wi-Fi credentials; UTM Shared networking uses the host uplink through virtual NAT. Never put credentials, API keys, cookies, student data, or personal files in the build context.
