# Building the prototype ISO

The active development builder produces the same Ubuntu 26.04 LTS/Plasma 6 live system for `amd64` and `arm64`, using architecture-specific kernels, package archives, bootloader packages, build caches, output names, and metadata. Common desktop, AI, visual assets, themes, apps, and configuration are shared. The former XFCE implementation is preserved in branch `legacy/xfce4` and `scripts/build-iso-xfce4-legacy-container.sh`.

Requirements: Docker Desktop with at least 8 GB RAM, 30 GB free disk, and network access. Build AMD64 with `./scripts/build-iso.sh --arch amd64` and ARM64 with `./scripts/build-iso.sh --arch arm64`. Omitting `--arch` preserves AMD64 as the default. The helper container uses Ubuntu 24.04 tooling to debootstrap the Ubuntu 26.04 (`resolute`) target; using the 26.04 host container reproduced a `tar failed` error while extracting `base-files`, whereas the 24.04 host container completed that bootstrap. AMD64 uses the official Ubuntu archive; ARM64 uses the official Ubuntu ports archive. On Apple Silicon, ARM64 build tools run natively in Docker and AMD64 uses emulation. The scripts preserve the existing AMD64 cache and use a separate ARM64 cache and rootfs. Both EFI targets install `mtools`, which `grub-mkrescue` needs when creating the EFI FAT image. Removing a cache volume discards its cached target rootfs. Set `IFBA_BUILD_CACHE_VOLUME` to use an explicitly named cache volume.

Before each ISO build, assign a new product version in `tools/build_metadata.py` and commit the build inputs first. Each build embeds version, architecture, build ID, source commit, and UTC time in `/usr/share/ifba-os/build-info.json`; `ifba-os-version` prints these fields in the live system. Artifacts and `.manifest.json` sidecars distinguish architecture and version, for example `output/ifba-os-ubuntu-26.04-arm64-v0.3.0.iso`. The sidecar records the final SHA-256 and byte size because embedding an ISO's own final hash would alter its bytes. After each successful build, record the identity and actual runtime checks in `ISO-RELEASES.md` in a separate documentation-only commit. The shared Plasma builder checks wallpaper, IFBA color scheme, SDDM, Plasma packages, Firefox, IFBA AI, SUAP/AVA launchers, DHCP profile, and build metadata before SquashFS creation.

The Plasma builder includes SDDM, Plasma 6 Wayland and X11 sessions, KWin, Dolphin, Konsole, Discover, System Settings, NetworkManager/audio widgets, a project color scheme and a native Plasma global-theme package. Its first-run layout defines a dark floating bottom panel configured for full-width length, with Kickoff, task switching, the system tray and clock; IFBA AI, Firefox, Dolphin and Konsole are included in task-manager launchers. SDDM starts the live account into the X11 Plasma session for the UTM prototype. The one-time session setup applies the user-supplied wallpaper and layout without resetting later wallpaper preferences. The existing Python/GTK assistant backend/service, Mozilla Firefox DEB and ordinary SUAP/AVA links are preserved. For ARM64 v0.3.0, the ISO structure and AArch64 UEFI payload were checked, but no UTM guest boot has been validated yet; wallpaper, panel styling, SDDM, network, Firefox and assistant startup still need runtime checks.

The Electron source under `app/` is a separate design prototype; the ISO does not include or autostart it. KWin is the compositor and window manager in the new build; no second compositor is installed. Animation modes, window decoration refinements, launcher interactions and background blur have not yet been implemented or validated.

The educational package catalogue is not installed by this image. The GTK assistant settings/chat window, user-scoped D-Bus service, private SQLite data directory, Secret Service integration, NVIDIA text stream, and source-level consent-based visual guidance are included. The visual/X11 dependencies are `python3-xlib`, `python3-pyatspi`, and `at-spi2-core`. The current output ISO must be rebuilt after these visual changes. The assistant has not made a live authenticated request. The live ISO auto-logs into a shared passwordless `ubuntu` account, so do not configure personal API keys or real student data in this demo; it does not provide per-student account isolation. The image has no installer or disk persistence. The generated IFBA identity is provisional. Do not boot this image on real hardware or present it as an official IFBA release.

The build removes the container's systemd-resolved stub before SquashFS creation so the live guest can configure DNS itself. It does not embed host Wi-Fi credentials; UTM Shared networking uses the host uplink through virtual NAT. Never put credentials, API keys, cookies, student data, or personal files in the build context.
