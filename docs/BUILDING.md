# Building the prototype ISO

The active development builder produces the same Ubuntu 26.04 LTS/Plasma 6 live system for `amd64` and `arm64`, using architecture-specific kernels, package archives, bootloader packages, build caches, output names, and metadata. Common desktop, AI, visual assets, themes, apps, and configuration are shared. The former XFCE implementation is preserved in branch `legacy/xfce4` and `scripts/build-iso-xfce4-legacy-container.sh`.

Requirements: Docker Desktop with at least 8 GB RAM, 30 GiB free disk, and network access. Build a matched release with `./scripts/build-iso.sh --both`; build one architecture with `./scripts/build-iso.sh --arch amd64` or `--arch arm64`. Release builds require a clean committed worktree. `--both` captures one source commit and product version, builds ARM64 then AMD64 with distinct build IDs/manifests, validates both, and advances `output/latest/` to the complete pair. A single-architecture build remains in `.staging/` and never changes `latest/`. The build checks the 30 GiB minimum before creating staging files. A verified pair is archived under `output/versions/vX.Y.Z/{arm64,amd64}/`. The publisher advances per-file symlinks under `latest/` and marks `release-status.json` complete after both references are in place. Existing ISO paths are preserved and legacy regular manifests are retained beside the matching ISO name. The container bootstraps a new Resolute rootfs for each build and upgrades it before package selection. The architecture-specific Docker volume caches only verified debootstrap package downloads. Package versions come from the moving release/security repositories. The helper container uses Ubuntu 24.04 tooling to debootstrap the Ubuntu 26.04 (`resolute`) target, using the standard Ubuntu `gutsy` script when that tool package lacks the Resolute alias; the 24.04 host container completed the bootstrap that failed under the 26.04 host container. AMD64 uses the official Ubuntu archive; ARM64 uses Ubuntu Ports. On Apple Silicon, ARM64 build tools run natively in Docker and AMD64 uses emulation. The scripts preserve separate caches/rootfs trees. Both EFI targets install `mtools`, which `grub-mkrescue` needs for the EFI FAT image. New volumes are named `ifba-os-bootstrap-resolute-<arch>`. Set `IFBA_BUILD_CACHE_VOLUME` to use a different package cache volume. Older rootfs cache volumes do not supply files to the new layout.

Set the shared product release version in `tools/build_metadata.py` and commit all build inputs before building. Both architectures of a release must embed the same source commit and version; build IDs and hashes remain architecture-specific. `scripts/build-iso.sh --both` is the preferred matched-release command. It captures one HEAD and version, stages each architecture in a distinct filename/metadata file, verifies both, and only then archives the pair and advances `output/latest/{amd64,arm64}/` with per-architecture `manifest.json` links. It refuses dirty source and checks that HEAD did not change during the build. `tools/release_artifacts.py list|verify|migrate` lists, verifies, and can organize legacy artifacts; verification checks SHA-256, size, ISO 9660/El Torito descriptors, boot-catalog architecture and volume label. The container extracts the finished ISO's kernel, initrd, root filesystem and GRUB configuration, checks the root-level Casper `md5sum.txt` against those extracted Live payload files and `filesystem.size`, then compares embedded build metadata with the requested build. The list excludes GRUB-generated boot images and catalogs and the checksum file itself. The external ISO SHA-256 remains the release integrity check. `latest/release-status.json` states whether both architecture artifacts share the same version and source commit. **Current local artifacts (2026-11-22):** `output/latest/arm64/` retains the v0.3.6 ARM64 ISO because a running historical UTM VM reports that filename, though its backing path is not known. `output/latest/amd64/` has a v0.3.6 manifest but no ISO; `release-status.json` therefore records `complete_pair: false`. The new v0.3.8 ARM64/AMD64 pair is archived under `output/versions/v0.3.8/`, structurally verified, and runtime-unvalidated. It was not promoted into `latest/` to preserve the potentially attached VM media. The prior v0.3.5 pair is preserved under `output/versions/v0.3.5/`; the v0.3.3 ARM64 ISO remains under `output/versions/` because a historical UTM VM references that path. Historical release identities remain in `ISO-RELEASES.md`. The manifest records source commit, UTC build time, architecture, unique build ID, runtime status, SHA-256, and exact byte size. The builder checks wallpaper, IFBA color scheme, SDDM, Plasma packages, Firefox, IFBA AI, SUAP/AVA launchers, DHCP profile, and build metadata before SquashFS creation.

The Plasma builder includes SDDM, Plasma 6 Wayland and X11 sessions, KWin, the native Aurorae window-decoration engine, Dolphin, Konsole, Discover, System Settings, NetworkManager/audio widgets, PipeWire Audio/WirePlumber/Pulse compatibility, FFmpeg media codecs, BlueDevil, Milou search, KInfoCenter, PowerDevil/UPower and the IFBA color scheme. The top panel uses native Kickoff, appmenu, system tray and clock applets; the status tray exposes NetworkManager, volume, battery, Bluetooth and notifications. The custom aggregated Control Center was removed from the build because its private QML imports were never runtime-validated. The floating dock uses the audited Matt-Anis Plasma 6 plasmoid, with upstream attribution and license retained. KScreenLocker now uses the installed `org.kde.plasma.desktop` shell and the IFBA lock-screen wallpaper; the previously derived shell and custom lock-screen QML were removed from the image path. New/live profiles select the stock shell, and the build migrates only the obsolete `ShellPackage=org.ifbaos.plasma` setting while preserving unrelated user config. Static regressions cover that migration and ensure the retired plasmoid is not packaged. Actual login/lock-screen, applet popups, wallpaper, authentication and appearance still require a fresh guest test. IFBA OS ships its own SVG Aurorae decoration, `IFBA OS Window Frame`, with a 34 px title area, native minimize/maximize/close controls following the upstream WhiteSur order, active/inactive and hover states, graphite frame, 12 px rounded corners and maximized-state assets. New live and created-user profiles receive this setting via the packaged global-theme defaults. Qt/GTK applications using server-side KWin decorations follow it; applications that draw their own client-side titlebars can override it. The decoration package and SVG/config contracts are statically checked, but behavior in the current ISO, on both architectures, and across Dolphin, Konsole, Firefox and native/client-side decorated apps remains pending a rebuild and real desktop session. SDDM continues to use Breeze with IFBA wallpaper, accent and institutional symbol. Plasma applies the Look-and-Feel layout and wallpaper when there are no saved containments. The IFBA autostart handles only migration of the old window button order. The Live SDDM autologin selects Plasma Wayland, matching Casper, and Calamares strips the Live autologin. The installed greeter initially selects Plasma X11 and remembers subsequent user choices.

The Electron source under `app/` is a separate design prototype; the ISO does not include or autostart it. KWin is the compositor and window manager in the new build; no second compositor is installed. The IFBA Aurorae decoration provides a subtle KWin-managed shadow and hover transition; visual appearance and window interactions need runtime validation after rebuilding the ISO. No second decoration plugin or fake client-side frame is used.

The build includes the native Qt 6 IFBA Welcome app, which autostarts for KDE sessions and stores the user's “do not show again” choice in their config directory. It links the existing public SUAP/AVA sites, IFBA AI, local help, Discover's updates page, and installed VSCodium, LibreOffice Writer, and GCompris executables. VSCodium is pinned to version 1.143.17232 from `repo.vscodium.dev`; the build verifies its signing-key fingerprint and architecture-specific package hashes before installing. The binaries use MIT licensing and the extension registry is Open VSX; some extensions limited to Microsoft Visual Studio Marketplace are unavailable. It does not read academic data or ask for credentials. The GTK assistant settings/chat window, user-scoped D-Bus service, private SQLite data directory, Secret Service integration, NVIDIA text stream, and source-level consent-based visual guidance are included. The visual/X11 dependencies are `python3-xlib`, `python3-pyatspi`, and `at-spi2-core`. The matched v0.3.8 images under `output/versions/v0.3.8/` include VSCodium and passed structural verification; runtime remains unvalidated. They were not published under `latest/` because the running UTM VM may reference the existing ARM64 media. Both v0.3.8 ISOs exceed GitHub’s 2 GiB per-asset limit and remain available locally. The assistant has not made a live authenticated request. The live ISO auto-logs into a shared passwordless `ubuntu` account, so do not configure personal API keys or real student data in this demo; it does not provide per-student account isolation. The v0.3.7 images include the Welcome app and experimental Calamares candidate; the installer has not passed a real installation, reboot, and login test. The updated build recipe includes an experimental Calamares installer that has not passed a real installation, reboot, and login test; see [`INSTALLER.md`](INSTALLER.md). The generated IFBA identity is provisional. Do not boot this image on real hardware or present it as an official IFBA release.

The build removes the container's systemd-resolved stub before SquashFS creation so the live guest can configure DNS itself. It does not embed host Wi-Fi credentials; UTM Shared networking uses the host uplink through virtual NAT. Never put credentials, API keys, cookies, student data, or personal files in the build context.

Desktop palette, typography and visual tokens are defined in `packaging/design-system/tokens.json`; run `python3 tools/generate_design_system.py` to regenerate the KDE color scheme, Konsole colors, GTK 3/4 CSS/settings and IFBA AI stylesheet. `scripts/build-iso.sh` rejects stale generated assets before starting a release build. System GTK defaults and the new-user skeleton are packaged alongside the Plasma/KDE scheme; existing home-directory GTK and KDE settings are kept. See [`DESIGN-SYSTEM.md`](DESIGN-SYSTEM.md). These file contracts are automated; GTK/Qt appearance and contrast still require screenshots from a real guest session.

## Boot animation

The builder converts `assets/animations/boot animation.mp4` to 12 FPS PNG frames for Plymouth and selects the IFBA OS theme before rebuilding the initramfs. The video supplies the imagery. The runtime theme advances from Plymouth's boot timer and holds the final frame if startup continues. A fast boot may leave the splash before the clip ends. Plymouth uses a static image outside the boot animation, and retains the boot message and disk-unlock prompts.

The Live GRUB entry passes `quiet splash`. Calamares runs its `grubcfg` module before writing the installed bootloader so it can enable the same Plymouth splash on the target. The build checks that every theme file is present in the initramfs and verifies the copy extracted from the ISO.
