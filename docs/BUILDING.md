# Building the prototype ISO

The active development builder produces the same Ubuntu 26.04 LTS/Plasma 6 live system for `amd64` and `arm64`, using architecture-specific kernels, package archives, bootloader packages, build caches, output names, and metadata. Common desktop, AI, visual assets, themes, apps, and configuration are shared. The former XFCE implementation is preserved in branch `legacy/xfce4` and `scripts/build-iso-xfce4-legacy-container.sh`.

Requirements: Docker Desktop with at least 8 GB RAM, 30 GiB free disk, and network access. Build a matched release with `./scripts/build-iso.sh --both`; build one architecture with `./scripts/build-iso.sh --arch amd64` or `--arch arm64`. Release builds require a clean committed worktree. `--both` captures one source commit and product version, builds ARM64 then AMD64 with distinct build IDs/manifests, and publishes only verified artifacts. A single-architecture build never advances `latest/` to an incomplete newer release. Before package selection, the container upgrades the cached rootfs with `apt-get upgrade --with-new-pkgs`; package versions still come from the moving release/security repositories and are not locked to a snapshot. The helper container uses Ubuntu 24.04 tooling to debootstrap the Ubuntu 26.04 (`resolute`) target; the 24.04 host container completed the bootstrap that failed under the 26.04 host container. AMD64 uses the official Ubuntu archive; ARM64 uses Ubuntu Ports. On Apple Silicon, ARM64 build tools run natively in Docker and AMD64 uses emulation. The scripts preserve separate caches/rootfs trees. Both EFI targets install `mtools`, which `grub-mkrescue` needs for the EFI FAT image. Removing a cache volume discards its cached target rootfs. Set `IFBA_BUILD_CACHE_VOLUME` to use an explicitly named cache volume.

Set the shared product release version in `tools/build_metadata.py` and commit all build inputs before building. Both architectures of a release must embed the same source commit and version; build IDs and hashes remain architecture-specific. `scripts/build-iso.sh --both` is the preferred matched-release command. It captures one HEAD and version, stages each architecture in a distinct filename/metadata file, verifies both, and publishes to `output/versions/vX.Y.Z/{amd64,arm64}/` with `manifest.json`. It refuses dirty source and checks that HEAD did not change during the build. `tools/release_artifacts.py list|verify|migrate` lists, verifies, and safely organizes local artifacts; verification checks SHA-256, size, ISO 9660/El Torito descriptors, boot-catalog architecture and volume label. The container extracts the finished ISO's kernel, initrd, root filesystem and GRUB configuration, then compares embedded build metadata with the requested build. `output/latest/{amd64,arm64}/` uses symlinks to avoid duplicating ISO files; `release-status.json` states whether both pointers form a matched release. **Existing local artifacts:** v0.3.2 ARM64 and AMD64 are a matched pair from source commit `7d5b1507c028c3e7e6aca8237f548815c539ca38`; `latest/release-status.json` records `complete_pair: true`. Their hashes, sizes, and build IDs are in `ISO-RELEASES.md`. They predate the NetworkManager, IFBA AI, Plasma and Konsole fixes committed as `e86fa66`. Version 0.3.3 is prepared for the next matched build from its own committed source state. The manifest records source commit, UTC build time, architecture, unique build ID, runtime status, SHA-256, and exact byte size. The builder checks wallpaper, IFBA color scheme, SDDM, Plasma packages, Firefox, IFBA AI, SUAP/AVA launchers, DHCP profile, and build metadata before SquashFS creation.

The Plasma builder includes SDDM, Plasma 6 Wayland and X11 sessions, KWin, the native Aurorae window-decoration engine, Dolphin, Konsole, Discover, System Settings, NetworkManager/audio widgets, Milou search, KInfoCenter, PowerDevil/UPower and a project color scheme with native Plasma global-theme defaults. KScreenLocker uses a build-generated `Plasma/Shell` package copied from the installed desktop shell for that exact build; only its two lock-screen QML entry files are replaced, while the package-owned shell remains untouched. This gives the session and KScreenLocker the same shell package ID and preserves the rest of the desktop shell. The QML uses KScreenLocker's PAM-backed authenticator and system-gated `SessionManagement` actions. Lock-screen wallpaper, shell-package creation, defaults for the live account and `/etc/skel`, and static QML/build contracts are covered by tests; graphical rendering, authentication, Wayland behavior, error logs, repeated locking, scaling, and resource use still require a real Plasma guest test. IFBA OS ships its own SVG Aurorae decoration, `IFBA OS Window Frame`, with a 34 px title area, right-side minimize/maximize/close controls, active/inactive and hover states, graphite frame, 12 px rounded corners and maximized-state assets. New live and created-user profiles receive this setting via the packaged global-theme defaults. Qt/GTK applications using server-side KWin decorations follow it; applications that draw their own client-side titlebars can override it. The decoration package and SVG/config contracts are statically checked, but behavior in the current ISO, on both architectures, and across Dolphin, Konsole, Firefox and native/client-side decorated apps remains pending a rebuild and real desktop session. The bottom dock is a native 70 px floating panel with fit-to-content centering, intelligent window-dodge hiding, IFBA Kickoff, icon-only tasks, installed educational-app launchers and the native Trash applet. Its task applet has manual ordering, application grouping, tooltips, user-configurable hover behavior (off by default), and runtime checks for each packaged launcher and widget. Dock layout and package contracts are tested statically; graphical behavior, drag reorder, context menus, task indicators and scaling await validation in a fresh Plasma session. SDDM starts the live account into the X11 Plasma session for the UTM prototype. The one-time session setup applies the user-supplied wallpaper and layout without resetting later wallpaper preferences. The existing Python/GTK assistant backend/service, Mozilla Firefox DEB and ordinary SUAP/AVA links are preserved. For ARM64 v0.3.0, the ISO structure and AArch64 UEFI payload were checked, but no UTM guest boot has been validated for this source state.

The Electron source under `app/` is a separate design prototype; the ISO does not include or autostart it. KWin is the compositor and window manager in the new build; no second compositor is installed. The IFBA Aurorae decoration provides a subtle KWin-managed shadow and hover transition; visual appearance and window interactions need runtime validation after rebuilding the ISO. No second decoration plugin or fake client-side frame is used.

The build includes the native Qt 6 IFBA Welcome app, which autostarts for KDE sessions and stores the user's “do not show again” choice in their config directory. It links the existing public SUAP/AVA sites, IFBA AI, local help, Discover's updates page, and installed Thonny, LibreOffice Writer, and GCompris executables. It does not read academic data or ask for credentials. The GTK assistant settings/chat window, user-scoped D-Bus service, private SQLite data directory, Secret Service integration, NVIDIA text stream, and source-level consent-based visual guidance are included. The visual/X11 dependencies are `python3-xlib`, `python3-pyatspi`, and `at-spi2-core`. The current output ISO must be rebuilt after these changes. The assistant has not made a live authenticated request. The live ISO auto-logs into a shared passwordless `ubuntu` account, so do not configure personal API keys or real student data in this demo; it does not provide per-student account isolation. The current output ISOs do not include the Calamares candidate or IFBA Welcome changes. The updated build recipe includes an experimental Calamares installer that has not passed a real installation, reboot, and login test; see [`INSTALLER.md`](INSTALLER.md). The generated IFBA identity is provisional. Do not boot this image on real hardware or present it as an official IFBA release.

The build removes the container's systemd-resolved stub before SquashFS creation so the live guest can configure DNS itself. It does not embed host Wi-Fi credentials; UTM Shared networking uses the host uplink through virtual NAT. Never put credentials, API keys, cookies, student data, or personal files in the build context.
